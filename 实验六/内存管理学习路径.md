# 实验六：内存管理学习路径与代码导读

这份学习路径针对当前 `06.MemoryManage` 项目，目标是让你能解释内存、独立使用内存池，并读懂分配与释放的实现。建议按七个阶段学习，每阶段约 1～2 小时；遇到指针不熟悉，可以先多花时间补基础。

本文依据项目源码和现有工程配置整理；没有进行本次编译、下载或硬件验证。文中的实验预期用于指导你在开发板上观察，不能当作已经测得的结果。

## 一、先知道这个项目在做什么

这是一个 GD32F303ZE 的裸机内存管理演示工程，使用 Keil 工程组织代码。它准备两块内存池，让你通过触摸屏申请、释放内存，并观察使用量和曲线。

| 项目内容 | 当前代码配置 |
| --- | --- |
| 内部内存池 | `SRAMIN`，可分配数据区 20 KiB |
| 外部内存池 | `SRAMEX`，可分配数据区 928 KiB |
| 分配粒度 | 两个池都以 32 字节为一块 |
| 内部申请按钮 | 每次申请 1 KiB |
| 外部申请按钮 | 每次申请 50 KiB |
| 外部数据区起始地址 | `0x6C000000` |
| 使用率接口 | `MemoryPerused()`，返回 0～1000，对应 0.0%～100.0% |

这里的池容量不是芯片全部 RAM 容量。工程配置的内部 RAM 区域为 64 KiB，其中还要放全局变量、栈、内存管理表、GUI 数据等；20 KiB 只是其中预留给本分配器的数据区。

外部池的宏实际是 `928 * 1024`，旁边注释却写 896K。阅读时以实际表达式为准，并结合后文的容量核查说明。

## 二、内存是什么、为什么要管理、怎么使用

### 1. 内存是什么

可以把内存理解为一排有编号的储物格。一个字节是一个基本存储单位；地址是格子的编号；变量是编译器根据类型和生命周期安排的存储对象；指针变量保存的是地址。

```c
u8 value = 10;
u8 *p = &value;
*p = 20;
```

逐句理解：

1. `value` 保存一个 8 位无符号整数，项目中 `u8` 是 `unsigned char`。
2. `&value` 取得变量地址，赋给指针 `p`。
3. `*p` 访问该地址指向的对象，所以执行后 `value` 变为 20。

必须区分 `p` 与 `*p`：前者是地址，后者是地址指向的内容。指针本身也需要存储空间，本项目的目标平台使用 32 位地址。

### 2. Flash、SRAM、栈、堆分别是什么

| 名称 | 是什么 | 本项目中如何理解 |
| --- | --- | --- |
| Flash | 掉电后通常仍保留内容的存储器 | 保存程序代码、常量和图片等资源 |
| SRAM | 运行时可读写、掉电丢失内容的存储器 | 保存变量、缓冲区及内存池 |
| 内部 SRAM | MCU 芯片内部的 SRAM | `Memory1Base` 所在区域 |
| 外部 SRAM | 通过总线连接到 MCU 的 SRAM | 经 EXMC 访问，`Memory2Base` 固定在外部地址 |
| 栈 | 用来支持函数调用及部分自动变量的运行区域 | 局部数组过大、调用层次过深会消耗栈空间 |
| C 库堆 | 通常由标准库分配器管理的动态存储区域 | 与本项目的自定义内存池分开理解 |
| 自定义内存池 | 提前划定、由自己的代码管理的空间 | `MyMalloc()`、`MyFree()` 操作的对象 |

栈、堆描述的是内存的组织和用途；内部、外部 SRAM 描述的是硬件存储位置，它们不是同一层面的分类。

项目实际加入工程的启动文件是 `ARM/System/startup_gd32f30x_hd.s`，其中栈预留 `0x3200` 字节，即 12.5 KiB，库堆预留 `0x400` 字节，即 1 KiB。`MyMalloc()` 的 20 KiB 内部池不受这个 1 KiB 库堆大小直接控制。不要误读 `Project/RTE/Device/` 下未被当前工程选用的同名启动文件。

### 3. 为什么要管理内存

例如程序接收到一张图片或一段串口数据，运行前未必知道需要多大的缓冲区。如果为所有情况一直预留最大数组，会长期占用 RAM。动态分配可以让空间在需要时交给某个模块，不再使用时归还给其他模块。

本项目的分配器主要负责回答三个问题：

1. 哪些块空闲？由管理表记录。
2. 哪些连续空间能满足本次请求？由分配算法查找。
3. 一次申请占了多少块，释放时要归还哪些块？由管理表中的块数记录。

空间大小固定、生命周期明确时，普通数组通常更容易管理；大小或生命周期随运行变化时，可以考虑动态分配。动态分配本身也要消耗管理空间和查找时间。

### 4. 内存使用的完整过程

```text
初始化内存池 → 申请空间 → 检查是否成功 → 写入和读取 → 释放空间 → 清空持有的指针
```

申请成功只代表获得了使用一段空间的权利，不代表其中的数据已清零。释放只把块标记为空闲，原来的字节内容不一定被擦除，也不能继续读取或写入。

### 1. 启动与初始化主线


`Proc2msTask()` 中条件是 `s_iCnt > 10`，因此按标志正常被处理的情况，每累计 11 次 2ms 标志才执行一次业务任务，名义上约 22ms。注释写“20ms”不能代替对代码条件的分析；实际时序还会受主循环执行耗时等影响。

曲线是另一条路径：`MallocTopTask()` 每累计至少 250ms 读取一次两个池的使用率，将整数百分比交给 `addMemoryWave`；`GUITask()` 中曲线重绘另有大于 1000ms 的条件。采样与重绘要分开理解。

### 3. 回调为什么能连接两个模块

`StructGUIDev` 中的这些成员是函数指针：

```c
void (*mallocInButtonCallback)(void);
void (*updateInSRAMInfo)(u32 usage, u32 free);
```

`InitMallocTop()` 把业务回调交给 GUI；`InitGUI()` 又把显示更新函数写回结构体。GUI 收到按钮事件后调用回调，业务层申请完空间后调用显示函数。

需要理解：给函数指针赋值是在保存“以后调用谁”；写 `函数指针()` 才是实际调用。`s_structGUIDev` 使用静态存储期，是因为 GUI 保存了它的地址并在初始化结束后继续使用。

## 四、内存池核心算法：必须能自己画出来

### 1. 数据区和管理表

`Memory1Base`、`Memory2Base` 是交给申请者使用的字节数组。

`Memory1MapBase`、`Memory2MapBase` 是管理员自己使用的 `u32` 数组。每个表项对应数据区的一个 32 字节块：

- 值为 0：这个块空闲。
- 值为 N：这个块属于一次占 N 块的分配。该分配的每个表项都写入相同的 N。

例如在一个简化的 8 块池中申请 70 字节，需要 `ceil(70 / 32) = 3` 块：

```text
块编号：  0   1   2   3   4   5   6   7
申请前：  0   0   0   0   0   0   0   0
申请后：  0   0   0   0   0   3   3   3
                              ↑ 返回第5块首地址
```

算法从表尾向前扫描，因此在空池中先使用高地址附近的空间。随后申请一块，通常会获得更低地址；释放后再次申请可能复用原地址，不能把地址是否重复作为成功与否的判断依据。

### 2. `MallocMemory()` 的步骤

1. 如果该池未初始化，调用初始化函数。
2. 请求 0 字节时返回失败标记 `0xFFFFFFFF`。
3. 用除法和余数把请求字节数向上换算成块数。
4. 从最后一个管理表项向前扫描，统计连续空闲块。
5. 遇到已占用块，就把连续计数清零。
6. 找到足够长的连续区间后，把该区间每个表项都写成分配块数。
7. 返回相对池首地址的字节偏移；找不到则返回失败标记。

`MyMalloc()` 再把偏移变成真正地址：

```text
返回地址 = memoryBase[memx] + offset
```

内部的 `0xFFFFFFFF` 是偏移失败标记，对外则转换成 `NULL`。调用者应检查 `NULL`，不必接触内部偏移协议。

### 3. `FreeMemory()` 的步骤

1. 根据偏移除以块大小，得到起始块索引。
2. 从起始管理表项读取该次分配占用的块数。
3. 把对应数量的管理表项设为 0。

`MyFree()` 接收实际指针，先减去池首地址，得到偏移后交给 `FreeMemory()`。

这里必须传回分配时得到的原始首地址，不能传 `p + 1` 或分配区间中间某个块的地址。当前实现没有完整检查分配边界，错误指针可能破坏管理表。

### 4. 块大小与管理成本

| 数据区 | 块数 | 管理表大小 | 数据区与管理表合计 |
| --- | --- | --- | --- |
| 内部 20 KiB | 640 | 640 × 4 = 2560 字节，即 2.5 KiB | 22.5 KiB |
| 外部 928 KiB | 29696 | 29696 × 4 = 118784 字节，即 116 KiB | 1044 KiB |

每 32 字节数据区需要 4 字节管理信息，所以管理表大小是数据区大小的 12.5%。申请 1、31、32 字节都占 1 块；申请 33 字节占 2 块，这种块内未利用的空间称为内部碎片。

即使总空闲空间足够，如果空闲块分散，找不到足够长的连续区间，申请仍会失败。这是外部碎片问题，本实现不会自动搬移已有数据来整理空间。

## 五、哪些函数必须掌握

### A 类：必须会独立调用和解释

| 函数 | 必须掌握的内容 |
| --- | --- |
| `InitMemory(u8 memx)` | 初始化管理表；启动时调用；已有有效分配时不能随意重新初始化 |
| `MyMalloc(u8 memx, u32 size)` | 按字节申请，返回首地址或 `NULL`；池编号只能是 `SRAMIN` 或 `SRAMEX` |
| `MyFree(u8 memx, void *ptr)` | 在原池释放原始首地址；释放后将自己持有的指针设为 `NULL` |
| `MemoryPerused(u8 memx)` | 返回值不是直接百分数；250 表示 25.0%；统计的是池内已占用块 |
| `MyRealloc(u8 memx, void *ptr, u32 size)` | 看懂申请新区、复制、释放旧区的思路；识别当前实现缺陷，修正前避免直接用于通用扩容 |

`InitMemory()` 只清管理表，不会清空整个数据区。已有指针时重新初始化，会让分配器以为所有块均空闲，后续分配可能覆盖仍在使用的数据。

### B 类：必须读懂实现，能手算执行结果

| 函数 | 必须解释清楚的问题 |
| --- | --- |
| `MallocMemory()` | 如何向上取整？为什么倒序扫描？何时申请失败？ |
| `FreeMemory()` | 如何从地址偏移找到表项？为什么要求原始首地址？ |
| `SetMemory()` | 如何逐字节填充？管理表字节数为什么是表项数乘 4？ |
| `CopyMemory()` | 如何逐字节复制？复制长度为什么必须同时考虑源和目标容量？ |

这四个函数是 `static` 内部函数，应用模块通常不直接调用。`SetMemory()`、`CopyMemory()` 分别类似按字节操作的 `memset()`、`memcpy()`；当前 `CopyMemory()` 不提供重叠区间复制保证。

### C 类：读懂项目如何运行

| 函数 | 掌握目标 |
| --- | --- |
| `main()`、`InitHardware()`、`InitSoftware()` | 讲清初始化顺序和主循环 |
| `InitEXMC()`、`ConfigBank0Region3()` | 讲清外部池访问依赖总线、地址映射和时序 |

## 六、怎么写：从最小示例开始

### 1. 申请、写入、读取、释放

以下函数是学习示例，没有自动加入固件。可将它放在能包含 `Malloc.h` 的源文件中，在内存池初始化完成后单次调用。初始化工作由项目原有 `InitSoftware()` 完成，示例中不重复初始化。

```c
#include "Malloc.h"
#include <stdio.h>

void MemoryBasicDemo(void)
{
    u32 i;
    u8 *buffer;

    buffer = MyMalloc(SRAMIN, 100);
    if (buffer == NULL)
    {
        printf("allocation failed\r\n");
        return;
    }

    for (i = 0; i < 100; i++)
    {
        buffer[i] = (u8)i;
    }

    printf("first=%u, last=%u\r\n",
           (unsigned int)buffer[0],
           (unsigned int)buffer[99]);

    MyFree(SRAMIN, buffer);
    buffer = NULL;
}
```

理解要点：100 字节请求占 4 块，即 128 字节，但业务代码仍按自己申请的 100 字节边界使用。`buffer[100]` 不属于本例约定的数据范围。不能把内存池指针交给标准库 `free()`。

如果申请的是 `u32` 数组，字节数应写成 `元素个数 * sizeof(*指针)`，而不是只写元素个数。元素数来自外部输入时，还应先检查乘法是否溢出及长度是否合理。

### 2. 准确理解使用率

```c
u16 rate;

rate = MemoryPerused(SRAMIN);
printf("usage=%u.%u%%\r\n",
       (unsigned int)(rate / 10),
       (unsigned int)(rate % 10));
```

`MemoryPerused()` 使用整数除法，结果会向下截断。例如空的内部池申请 100 字节，占 4 块，返回 `4 * 1000 / 640 = 6`，显示 0.6%，而真实块占用比例是 0.625%。

因此不能通过这个返回值无损还原已用字节数。它只统计该内存池，不包含 MCU 上所有变量、栈或整个 SRAM 的使用量。

### 3. 跨函数保存内存时，必须明确谁释放

如果一个模块要长期持有一个缓冲区，可以采用以下模式：

```c
static u8 *s_buffer = NULL;

int CreateBuffer(void)
{
    u8 *newBuffer;

    if (s_buffer != NULL)
    {
        return 0; /* 已经持有一个缓冲区，拒绝重复创建 */
    }

    newBuffer = MyMalloc(SRAMIN, 1024);
    if (newBuffer == NULL)
    {
        return 0;
    }

    s_buffer = newBuffer;
    return 1;
}

void DestroyBuffer(void)
{
    if (s_buffer != NULL)
    {
        MyFree(SRAMIN, s_buffer);
        s_buffer = NULL;
    }
}
```

这段代码采用“一次只持有一个缓冲区”的规则。如果业务要同时持有多个分配，就需要数组或结构体分别记录每个指针及其池编号。把一个指针设为 `NULL` 不会自动清除其他别名指针，所以还要约定其他模块何时停止访问。

## 七、原项目中要辨清的实现问题

以下是源码分析发现的问题，本次只编写学习文档，未修改原有 C 源码。

### 1. 连续申请会丢失旧指针

两个申请回调都直接覆盖同一个 `s_pMalloc`。例如先申请内部 1 KiB，再申请内部 1 KiB，第一次分配仍占用内存，但程序只保存第二次的地址；之后按释放按钮只能释放最近一次分配。跨内部、外部申请也有同样问题。

申请失败时，直接把 `NULL` 写进原指针还可能丢失之前持有的地址。这不是分配器自动回收失败，而是上层没有保存每次分配的所有权信息。

改进方向：只允许一个有效分配时，重复申请前先检测；允许多个有效分配时，用记录表保存全部指针和池编号。新申请先交给临时指针，确认成功后再更新业务状态。

### 2. 释放后没有把指针清空

原 `FreeCallback()` 调用 `MyFree()` 后没有设置 `s_pMalloc = NULL`，变量仍保留旧地址。当前表项已清零时再次释放可能看似无事，但若该地址已被新对象复用，旧指针再次释放就可能影响新对象。

正确习惯是释放后清空持有指针，并保证不再通过任何别名访问已释放对象。

### 3. `MyRealloc()` 不能照搬标准库 `realloc()` 的用法

当前实现先申请 `size` 字节，再从旧指针直接复制 `size` 字节，最后释放旧区。它没有读取旧分配容量。

例如旧区只占 32 字节，新申请 100 字节，直接从旧区读取 100 字节就超出了旧分配范围。传入 `NULL` 且新分配成功时也会尝试从空地址复制。请求 0 字节时会返回失败而保留旧分配。

修正思路是记录或读取旧容量，只复制 `min(旧容量, 新容量)`，并明确处理空指针、0 字节请求、失败时保留旧对象等规则。若要求准确跟踪业务有效数据，还要单独保存有效数据长度。

因此在修正并验证前，先通过“申请新空间 → 按已知有效长度复制 → 释放旧空间”学习扩容，不要直接用本函数练习通用扩容。它也需要新旧区暂时同时存在，即使最终容量能容纳，也可能因为当前没有足够连续空闲区而失败。

### 4. 外部数据区和管理表可能超过实际芯片容量

当前外部数据区为 928 KiB，管理表为 116 KiB，总计 1044 KiB，覆盖半开地址区间：

```text
数据区： [0x6C000000, 0x6C0E8000)
管理表： [0x6C0E8000, 0x6C105000)
```

已有 map 文件也显示了这两个区域。若开发板实际只配备 1 MiB SRAM，那么末端超出 20 KiB。当前 GPIO 配置可见 A0～A18 地址线和 16 位数据总线，也提示需要核实物理容量和接线。

仅凭工程目录无法确认板上芯片型号，因此这里是条件性风险，不能直接断言硬件一定只有 1 MiB。应查看原理图和芯片型号，并确保“数据区 + 管理表 + 其他占用”都落在真实可用地址范围内。

若确认为 1 MiB、没有其他占用，896 KiB 数据区配 112 KiB 管理表总计 1008 KiB，是一种可核算的配置示例；不能仅因旧注释写了 896K 就未经硬件核实直接修改。

### 5. 界面字节数来自近似值

`updateMamInfoShow()` 先把千分比换成字节，再向上凑成 1 KiB 或 50 KiB 的整数倍。这针对按钮固定申请大小做了近似补偿，并非通用精确统计。

如果你加入 33 字节、100 字节等任意大小申请，文字显示可能与实际占用不同。精确统计应直接累计已占用块数乘以块大小；调试时同时看管理表与使用率，不能只看界面数字。

### 6. 参数检查与并发保护不完整

公开接口没有完整验证池编号；释放时也没有完整验证指针对齐、是否为分配首地址等条件。传入非法参数可能访问数组边界之外。

分配和释放会修改共享管理表，当前没有锁或临界区保护。主循环里的串行调用可以顺序执行；若以后加入 RTOS 多任务或在中断里也分配同一池，需要另外设计同步。当前查表算法耗时还随池大小变化，不宜直接放入要求很短响应时间的中断。

### 实验 A：块大小边界

在无其他占用的内部池中，依次“申请一个 → 观察 → 释放”，分别请求以下大小：

| 请求字节数 | 预期块数 | 预期块占用字节数 |
| --- | --- | --- |
| 1 | 1 | 32 |
| 31 | 1 | 32 |
| 32 | 1 | 32 |
| 33 | 2 | 64 |
| 100 | 4 | 128 |

池使用率只有千分之一分辨率，少量块的变化可能被截断，建议在调试器中观察管理表来确认。不要在每次实验之间对仍有有效指针的池重新调用初始化。

### 实验 B：20 KiB 内部池的容量上限

在确认内部池为空时，用一个含 21 个元素的指针数组保存连续 21 次 1 KiB 请求的结果。预期前 20 次成功，第 21 次返回 `NULL`；每个成功分配占 32 块，总共 640 块。

只释放保存到的成功指针，再全部清空。预期释放完使用率回到实验前的值。不要用原 GUI 的单个 `s_pMalloc` 来做这个实验，否则无法逐一找回所有分配。

### 实验 C：总空闲足够，但连续空间不够

在空的内部池中申请 20 个 1 KiB 区域并保存全部地址，交替释放其中 10 个。此时共空闲 10 KiB，但每段只有 1 KiB，预期申请 2 KiB 失败。

这能验证本实现需要连续空闲块。结束时释放其余有效指针，避免实验间相互干扰。

### 实验 D：观察原界面的指针覆盖

从内部池为空的状态开始，按两次内部申请，再按一次释放。预期仍有 1 KiB 占用，而程序已没有正常保存第一次分配的指针。此实验用于理解泄漏；完成后重新启动程序恢复干净状态，不要把反复重置管理表当成业务中的回收办法。

### 建议断点和观察变量

- `MyMalloc()` 返回处：看是否为 `NULL`，池编号和请求长度是否正确。
- `MallocMemory()` 找到区间的位置：观察 `nmemb`、`cmemb`、`offset`。
- `FreeMemory()`：观察 `index`、`nmemb` 和即将清零的表项范围。
- 两个申请回调：观察 `s_pMalloc` 被覆盖前后的值。
- `Memory1MapBase`：内部池管理表，适合最初的调试练习。

## 九、学完后应该能回答的问题与参考答案

### 1. 内存地址和地址里的数据有什么区别？指针变量本身存在哪里？

地址表示存储位置，数据表示该位置保存的内容。可以把地址理解为门牌号，把数据理解为房间中的物品。

```c
u8 value = 10;
u8 *p = &value;
```

这里 `p` 保存 `value` 的地址，`*p` 是该地址指向的值 10，`&p` 则是指针变量自身的地址。`p` 的类型是 `u8*`，`*p` 的类型是 `u8`，`&p` 的类型是 `u8**`。

指针变量本身也需要存储空间，其位置取决于声明方式及编译器安排：全局或静态指针通常位于静态存储区；普通局部指针可能位于栈或寄存器。指针自身的位置与它指向的数据位置可以不同，例如一个内部 RAM 中的指针可以保存外部 SRAM 的地址。

### 2. 为什么内部 SRAM 总容量不等于 `MEM1_MAX_SIZE`？

内部 SRAM 是硬件提供的总空间，`MEM1_MAX_SIZE` 只是从中预留给自定义分配器的数据区大小。

本项目工程配置的内部 RAM 为 64 KiB，但内部池数据区仅为 20 KiB。其余空间还要容纳管理表、栈、库堆、其他全局和静态变量等。内部池的管理表另外需要 2.5 KiB，因此不能把全部 SRAM 都设为可分配的数据区。

### 3. 为什么申请 33 字节实际占 64 字节？

本分配器按 32 字节整块分配，不能只分配某个块的一部分。33 字节超过一块容量，需要向上取整为两块：

```text
33 / 32 = 1，余数为1，因此再增加1块
占用字节数 = 2 × 32 = 64
```

其中额外的 31 字节属于块内未利用空间，即内部碎片。业务仍应按请求的 33 字节使用，不能把分配粒度当成随意访问额外空间的理由。

### 4. 本分配器为什么从高地址附近开始分配？

这是当前算法选择的搜索方向，不是动态分配必须遵守的规则。

`MallocMemory()` 从管理表最后一项开始，逐项向前扫描。管理表下标越大，对应的数据块地址越高，所以空池中的首次分配会落在高地址附近。找到足够的连续空闲块时，当前下标就是该区间的低地址起点。

后续分配未必一直向低地址移动：如果高地址的旧空间已释放，算法也可能先复用那里。更换扫描方向可以改变分配位置，但仍要保证连续块查找与管理表登记正确。

### 5. 管理表中的 3 表示 3 字节，还是本次分配占 3 块？

表示该表项所属的这次分配一共占 3 块。本项目每块 32 字节，所以这次分配的块容量为 96 字节。

例如申请 70 字节，会占用三个相邻块，管理表对应位置写成：

```text
[3][3][3]
```

每个表项都重复记录该次分配的块数。释放时，从原始首地址对应的表项读到 3，就知道需要清零三个表项。计算使用率时应统计三个非零表项，不能将它们相加误算为九块。

### 6. 为什么 `MyFree(SRAMIN, p + 1)` 不能用？

释放必须传入申请成功时得到的原始首地址。`p + 1` 已经改变地址，而且偏移多少字节取决于 `p` 指向的类型：`u8*` 前进 1 字节，`u32*` 在本平台前进 4 字节。

当前实现缺少完整验证，会把字节偏移量除以 32 得到管理表下标。如果偏移后仍落在首块，整数除法可能让它碰巧释放原分配，但这不代表用法正确。如果落入后面的块，就可能从错误位置开始清零，漏掉原分配的一部分，并错误释放后续对象的块，甚至越过管理表边界。

应始终保存并传回原始首地址，同时使用与申请时一致的内存池编号。

### 7. 为什么释放后不能继续使用旧地址，即使内容看起来没变化？

`MyFree()` 清除的是管理表中的占用记录，不会自动擦除数据区，因此旧内容可能暂时还看得到。但空间已经归还给分配器，可能随时分配给其他对象。

继续读取旧地址会得到不再可靠的数据，继续写入可能破坏新对象，这类问题称为释放后使用。应在使用结束后释放，并将自己持有的指针设为 `NULL`：

```c
MyFree(SRAMIN, p);
p = NULL;
```

这不会自动清除其他别名指针；如果多个模块保存了同一地址，还必须约定所有模块停止访问。释放同一分配也只能由约定的持有者执行一次。

### 8. 总空闲 10 KiB 时为什么申请 2 KiB 仍可能失败？

本分配器要求找到一段连续的空闲空间，总空闲量足够不等于最大连续空闲区足够。

例如十段各 1 KiB 的空闲区被仍在使用的块隔开，总计空闲 10 KiB，但最大连续空闲区只有 1 KiB，不能满足一次 2 KiB 请求。这是外部碎片问题。

当前算法不会自动移动已分配的数据来合并空闲区，因此会返回失败标记，上层 `MyMalloc()` 最终返回 `NULL`。

### 9. `MemoryPerused()` 返回 250 是多少百分比？为什么还原字节数会丢精度？

返回 250 表示 25.0%。它采用千分比形式保存结果：

```text
返回值 = 已用块数 × 1000 / 总块数
百分比 = 返回值 / 10.0
```

计算使用的是整数除法，小数部分会被截断。例如内部池共有 640 块，占用 4 块时：

```text
真实比例：4 / 640 = 0.625%
返回值：  4 × 1000 / 640 = 6
显示值：  0.6%
```

用 6 再换算字节数，已经无法恢复被截去的精度，所以不能精确还原 128 字节的块占用量。精确统计应直接使用“已用块数 × 32”，而不是先转使用率再反推。

### 10. 原 GUI 连续申请后为什么只能释放最近一次？

原申请回调每次都把新地址直接写进同一个 `s_pMalloc`。旧分配没有自动释放，但保存旧地址的变量被覆盖了：

```text
第1次申请：s_pMalloc → 区域A
第2次申请：s_pMalloc → 区域B，区域A仍占用但地址未被正常保存
释放按钮：只能根据当前记录释放区域B
```

如果新申请失败，直接写入 `NULL` 也可能覆盖旧地址。因此应先用临时指针检查申请结果。

若业务只允许一个缓冲区，就在已有有效分配时拒绝重复创建，或明确安排替换流程；若允许多个分配，就用数组或结构体分别保存每个原始首地址及其内存池编号，并逐一释放。不能通过重新初始化管理表来代替正常回收。

### 11. 为什么当前 `MyRealloc()` 在扩容时可能读取旧区之外的数据？

当前实现按新请求大小 `size` 直接复制：

```c
CopyMemory(新地址, ptr, size);
```

假设旧区只占 32 字节，现在申请 100 字节，它会从旧区连续读取 100 字节，多出的 68 字节超出了旧分配范围。`CopyMemory()` 自己不检查源区和目标区的容量，所以无法阻止这种错误。

正确实现应掌握旧容量和新容量，只复制两者的较小值；若业务知道有效数据长度，也应据此确定需要保留的字节数。同时明确处理 `ptr == NULL`、`size == 0` 和新申请失败等情况。

重新分配时应先申请并复制成功，再释放旧区；失败则保留旧区。接收结果时使用临时指针，避免失败返回 `NULL` 时丢失旧地址。当前项目函数修正前不宜直接用于通用扩容。

### 12. 外部 SRAM 配置为什么必须同时核算数据区与管理表？

因为当前实现把外部数据区和外部管理表都放在外部 SRAM 中，而且管理表紧跟在数据区之后；它们都占真实的芯片容量。

```text
数据区：928 KiB
块数：928 × 1024 / 32 = 29696
管理表：29696 × 4 = 118784字节 = 116 KiB
合计：928 + 116 = 1044 KiB
```

如果实际芯片只有 1 MiB，即 1024 KiB，合计就会超出 20 KiB。地址窗口足够大、链接器能够放置这些区域，并不代表物理芯片真的提供了这么多存储空间。

所以应先核实原理图、芯片型号和接线，再确保“数据区 + 管理表 + 其他外部占用”全部落在真实可用范围内。这里的 1 MiB 是条件示例，不能只凭源码断言开发板的实际容量。

能结合代码解释这些答案，并独立完成“申请、检查、读写、释放”的示例，就具备继续学习链表、消息队列、图像缓冲区与 RTOS 内存管理的基础。
