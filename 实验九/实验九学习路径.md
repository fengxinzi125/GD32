# 实验九学习路径 · SD 卡阅读器与汉字点阵

## 一、总览｜先看一个汉字经过哪些模块

实验八已经打通了“SD 卡 → FatFs → 阅读器”的路径。实验九沿用这条路径读取《西游记》，再增加一条“GBK 编码 → SPI Flash 字库 → LCD 像素”的路径。学完后，试着从任意一个汉字的两个文件字节出发，算出它在字库里的位置，并说清屏幕上的点是怎么画出来的。

| 数据 | 放在哪里 | 程序什么时候用 |
| --- | --- | --- |
| 《西游记》正文 | SD 卡 `0:/book/西游记.txt` | 打开首页、翻页或重新定位时分批读取 |
| 字库源文件 | SD 卡 `0:/font/GBK24.FON` | 上电时用于校验，发现字节差异时用于更新 |
| 24×24 字模 | 板载 GD25Q16 SPI Flash，从地址 `0` 开始 | 每画一个汉字时读取对应的 72 字节 |

建议打开 [Keil 工程](09.ChineseCharDisplay/Project/GD32KeilPrj.uvprojx)，按下面五步走。每一步先回答一个问题，再进入下一层。

## 二、分步学习｜顺着调用链往下读

### 第 1 步 · 找到开机和翻页入口

先在 [Main.c](09.ChineseCharDisplay/App/Main/Main.c) 里找到 `main()` 和 `InitSoftware()`。软件初始化先挂载 SD 卡，再调用 `InitFontLib()`，之后初始化 LCD，最后由 `InitFatFsTest()` 建立阅读界面并调用 `NextPage()` 显示首页。这样首次绘制书名或正文时，字库模块已经完成了启动处理。

再找触屏翻页的入口。主循环中的 `Proc2msTask()` 每累计处理 20 次 2 ms 标志，就调用一次 `FatFsTask()`。随后由 `GUITask()` 检查按钮，通过回调进入 `NextPage()` 或 `PreviousPage()`，最终由 `NewPage()` 绘制正文。实体键扫描排在 `FatFsTask()` 后面，因此翻页遇到 SDIO DMA 等待时，本轮实体键扫描也要等它返回。 [触屏回调](09.ChineseCharDisplay/App/EmbGUI/App/GUITop.c) · [阅读器入口](09.ChineseCharDisplay/App/FatFsTest/FatFsTest.c)

**自查**　首页和触屏下一页从哪里进入同一个绘制流程？在 `NextPage()` 和 `NewPage()` 处各找一次调用。

### 第 2 步 · 分清文件偏移、缓冲区下标和字符

在 [ReadBookByte.c](09.ChineseCharDisplay/App/FatFsTest/ReadBookByte.c) 里先读 `ReadData()`。它打开正文、定位到一批数据的起点、最多读取 5120 字节，然后关闭文件。`ReadBookByte()` 每次取一个字节，缓冲区耗尽且文件还有数据时再补读。正文的 `NewPage()` 遇到可打印 ASCII 就用一个字节绘制，遇到 GBK 双字节字符就再取一个字节，拼码后绘制。

**例子 A · 一个汉字跨过两批数据。** 假设「中」的高字节 `D6` 位于文件偏移 5119，低字节 `D0` 位于偏移 5120。第一次调用读走第一批的最后一个字节，`NewPage()` 暂存 `0xD600`。第二次调用发现缓冲区用完，从偏移 5120 补读，并取出第二批下标 0 的 `D0`。两次调用合起来得到 `0xD6D0`，屏幕上画一个字。

**例子 B · 翻回文件偏移 5200。** 若该位置处在正文内，`SetPosition()` 用整数除法算出批次 `5200 / 5120 = 1`，于是从文件偏移 5120 补读。再用取余算出 `5200 % 5120 = 80`，从缓冲区下标 80 继续。和实验八一样，翻页记录用的是文件字节偏移。这个偏移需要落在字符边界上，落在 GBK 的第二个字节就会从错误的位置开始解析。

**自查**　如果最后一批从偏移 5120 开始只读到 80 字节，文件已读到末尾时，阅读器还有多少字节能消费？先看实际读取量，再看缓冲区剩余量。最后这 80 字节的有效下标是 0 到 79。

### 第 3 步 · 把 GBK 编码换算成字模地址

在 [FontLib.c](09.ChineseCharDisplay/App/FontLib/FontLib.c) 里直接找 `GetCNFont24x24()`。字库把每个字模放在一个固定大小的槽位里。一个 24×24 字模有 576 个点，每个点用 1 位，因此每槽占 `576 / 8 = 72` 字节。

高字节从 `0x81` 到 `0xFE`。每个高字节对应 190 个槽位，低字节按 `0x40–0x7E`、`0x80–0xFE` 排列，中间跳过 `0x7F`。先确定字符是第几个槽位，再乘以每槽 72 字节。

| GBK 编码 | 槽位序号，从 0 开始 | SPI Flash 字节地址 |
| --- | ---: | ---: |
| `81 40` | 0 | 0 |
| `81 7E` | 62 | 4,464 |
| `81 80` | 63 | 4,536 |
| `D6 D0`（中） | 16,293 | 1,173,096 |

**例子 · 手算「中」。** 高字节 `D6` 前面有 `0xD6 - 0x81 = 85` 组，每组 190 槽。低字节 `D0` 位于跳过 `0x7F` 的那段，组内序号是 `0xD0 - 0x41 = 143`。所以字模地址是 `(85 × 190 + 143) × 72 = 1,173,096`，驱动从这里读连续 72 字节。

**自查**　为什么 `81 7E` 和 `81 80` 的字模地址只差 72 字节？试着用表里的两行反推代码中 `0x40` 和 `0x41` 的区别。

### 第 4 步 · 把 72 字节画成 24×24 像素

在 [LCD.c](09.ChineseCharDisplay/App/LCD/LCD.c) 找到 `ShowCNChar()`。函数取得字模后，从每个字节的最高位开始检查，先增加 `y`。画满一列的 24 个点后，`y` 回到起点，`x` 增加 1。每列正好使用 3 个字节。正文使用透明叠加，遇到 1 就画前景色，遇到 0 就保留原像素。

**例子 · 在纸上画第一列。** 假设前三个点阵字节是 `A0 00 01`，起点是 `(10, 20)`。`A0` 的二进制是 `10100000`，所以前 8 点里画 `(10, 20)`、`(10, 22)`。`00` 对应的 8 点保留背景。`01` 只有最后一位是 1，所以还会画 `(10, 43)`。第 4 个字节的最高位对应下一列的 `(11, 20)`。

正文横坐标每列增加 12 像素。假设一行从 `x = 6` 开始显示 `A中B`，三个字符的起点依次是 `6`、`18`、`42`。可以在 `NewPage()` 里对照 ASCII 的列计数加 1、汉字加 2。书名也会调用 `ShowCNChar()`，它从内存字符串经 `GUIDrawTextLine()` 和 `GUIDrawChar()` 到达 LCD。 [正文排版](09.ChineseCharDisplay/App/FatFsTest/FatFsTest.c) · [书名绘制](09.ChineseCharDisplay/App/EmbGUI/Platform/GUIPlatform.c)

### 第 5 步 · 回头看字库更新，练习分层排查

再读 [FontLib.c](09.ChineseCharDisplay/App/FontLib/FontLib.c) 的 `InitFontLib()`、`CheckFontLib()` 和 `UpdataFontLib()`。启动校验以 SD 卡上的字库为参照，从 SPI Flash 地址 `0` 开始逐批比较。发现差异后，更新函数从头分批写入，并按 `f_read()` 的实际读取量推进 Flash 地址。校验和更新所用的 SD 读取缓冲区都从内部 SRAM 申请，对应工程里的 SDIO DMA 传输约束。

**例子 · 最后一批只剩 104 字节。** 用一个 4200 字节的假想输入来模拟更新循环。第一批从文件偏移 0 读 4096 字节，写入 Flash 地址 0。第二批从偏移 4096 读 104 字节，写入 Flash 地址 4096。写入总量正好是 4200 字节。这里的 4096 是字库复制的分批大小，5120 是正文读取的分批大小，72 是单字模长度。三者都以字节计量，各自在不同的操作里使用。

| 现象 | 顺着哪一层查 |
| --- | --- |
| 串口显示挂载成功，随后打开字库或翻页失败 | 先看两个 `f_mount()` 的返回值和卷对象生命周期。当前代码传入的是函数内局部 `FATFS`，而 FatFs 会保存指针。函数返回后该对象已失效，后续文件操作需要仍然有效的卷对象。 |
| ASCII 正常，汉字乱码 | 先在 `NewPage()` 查看正文原始字节和 `cnChar`。用 `D6 D0` 检查拼码，再在 `GetCNFont24x24()` 检查地址和读回的 72 字节。 |
| 字库文件打不开，串口随后却打印校验成功 | 跟进 `CheckFontLib()` 的失败分支。当前代码在打开失败时返回 0，而 `InitFontLib()` 把 0 当作校验成功。结合前一条错误日志判断结果。 |

FatFs 的 `_CODE_PAGE = 936`、`_USE_LFN = 1` 用于处理中文长文件名。正文的 `f_read()` 读出的是原始字节，正文绘制函数按 GBK 解释它们。即使成功打开了 `西游记.txt`，也还要用十六进制视图确认正文编码。 [FatFs 配置](09.ChineseCharDisplay/TPSW/FatFs/src/ffconf.h)

## 三、回顾｜用一个小样本验收

有开发板时，把原字库放在 SD 卡的 `font/GBK24.FON`，用 GBK 编码保存一份内容为 `A中B` 的 `book/西游记.txt`。在 `ReadBookByte()`、`GetCNFont24x24()` 和 `ShowCNChar()` 依次观察文件字节、字模地址和绘点坐标。手头没有开发板时，可以用同一份输入在纸上走完这三个断点。

1. **读对字节。** 写出 `41 D6 D0 42`，并标出 `NewPage()` 消费了几次字节、绘制了几个字符。预期是读 4 字节，画 3 个字符。
2. **找对字模。** 从 `D6 D0` 算出槽位 16,293、Flash 地址 1,173,096，以及读取长度 72 字节。
3. **画对位置。** 用 `A0 00 01` 的点阵例子核对位序和扫描方向，再用 `A中B` 核对每个字符的横坐标。
4. **查对故障。** 假设出现“能打开书，但汉字乱码”，写下你要先观察的变量及其预期值。从正文的 `cnChar = 0xD6D0` 开始，再查 Flash 地址和 LCD 绘点。

把这条链画在笔记上，标出每一步传递的东西。`文件字节 → GBK 编码 → Flash 字节地址 → 72 字节点阵 → LCD 坐标`。随后挑一个别的汉字，用同样的方法独立走一遍。
